Everything here was inferred from reading the scripts that produce each file; I did not visually inspect the images/videos themselves (I can't view rendered pixel content directly in this pass), so descriptions are of *what the generating code computes and draws*, not a frame-by-frame visual description.

## `assets/geometry/` — 3D geometry

- **`assembly.mat`** — the master saved data: the full parts struct array `A` (name, body, category, color, mass, mesh vertices/faces, STL filename) plus the hardware parameter struct `H` used to generate it. Nearly everything downstream that needs 3D geometry (animators, previews, body-property calculations, the liquid-geometry bowl profile) loads this one file rather than regenerating meshes each time.
- **`parts_manifest.csv`** — a flat table of every part's name, rigid body group, category, and mass in grams — a quick way to see the full parts list and their masses without loading the `.mat` file.
- **One `.stl` file per part** (e.g. `Spoon_bowl.stl`, `VCA_A_winding.stl`, `Cflex_B10_fixed_1.stl`, etc.) — standard binary STL triangle meshes, in metres, one per named part in the assembly, generated by the hand-written `write_stl` helper inside `generate_rcflex_assets.m`. These could in principle be opened in any CAD viewer to inspect the geometry directly.

All of the above regenerate automatically: `START_PROJECT` rebuilds `assembly.mat` (and thus every STL) whenever the current `rcflex_parameters()` struct doesn't match the one cached inside the existing `assembly.mat` — you do not need to run the geometry generator by hand unless you're calling its lower-level functions directly.
