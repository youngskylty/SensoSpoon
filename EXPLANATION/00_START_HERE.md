# Start Here — Orientation to SensoSpoon

This folder (`EXPLANATION/`) is a set of notes explaining the codebase you inherited. It is **not** part of the project's own documentation (that's in `docs/`), and it is not tracked by git (it's listed in `.gitignore`). Nothing here proposes changes — it only explains what already exists, so you can find your way around before you touch anything.

## What SensoSpoon is

SensoSpoon is a concept for a hand-held eating utensil for people with hand tremor (essential tremor, Parkinson's, etc.). The idea: instead of a rigid spoon that transmits every shake of the hand straight into the bowl, the bowl sits on a small 2-axis gimbal (pitch and roll) built from **flexures** (thin metal pivots that bend elastically instead of using ball bearings). Two small linear motors (**voice-coil actuators**, VCAs) push and pull rods connected to that gimbal. A control system reads motion sensors, decides how hard to push each actuator, and tries to rotate the bowl in the *opposite* direction to the hand's tremor — so the bowl stays level in the world even while the hand shakes.

It's a simulation and analysis project, not firmware for a physical prototype. Everything — the geometry, the physics, the sensors, the control algorithm — is a MATLAB/Simulink model of a proposed hardware design. The `README.md` and `docs/*.md` files (written by the teammate who built this) are explicit that this is "an algorithm-development baseline," not a validated or manufacturable product, and that full tremor cancellation has not been achieved. Keep that framing in mind as you read: the code is honest about its own limitations in comments and docs, and this explanation set reports those limitations rather than editorializing about them.

## The physical concept, as a signal-flow story

Imagine the signal flow as a loop:

1. **The hand shakes.** This is the disturbance — modelled as "base motion": rotation (roll, pitch) and translation of the handle, driven either by a synthetic tremor generator or a recorded/synthetic waveform.
2. **Two IMUs sense motion.** An IMU (Inertial Measurement Unit — a chip with a gyroscope and accelerometer) sits in the handle, and a second one sits on the moving spoon carrier. Comparing the two tells the controller how the spoon is oriented *relative to* the hand.
3. **The controller estimates hand intent and computes a correction.** A filter separates "intentional slow hand movement" (which the spoon bowl should follow) from "tremor" (which it should cancel), then a PID-style control loop computes how much counter-rotation is needed.
4. **The controller commands current, which becomes force.** The attitude controller doesn't drive the motors directly — it asks for a certain electrical current in each voice coil. A second, faster control loop (a PI current controller) converts that request into an actual voltage sent to the coil.
5. **Electrical dynamics produce actuator force.** Voltage drives current through an RL circuit (resistor + inductor, like any real motor coil); current produces force via the coil's force constant.
6. **Force moves the mechanism.** The two actuator rods push on the gimbal through a fixed linkage geometry; the gimbal's rigid-body dynamics (mass, inertia, gravity, flexure spring stiffness, friction) determine how pitch and roll actually respond.
7. **The spoon (and any liquid in it) moves.** This is the physical result: the bowl's orientation and position in the world, and — in the separate liquid-slosh add-on — how soup in the bowl sloshes and possibly spills.
8. **Back to step 2**: the IMUs sense the new motion, and the loop continues.

Everything downstream of "the hand shakes" in this list is computed by the code you're inheriting. Step 1 (the disturbance) is itself synthetic, generated by test-case scripts — there's no real tremor-patient data.

## Two loops, not one

There's a slower **outer loop** (attitude control, 800 Hz) that decides "how much current do I want in each coil," and a much faster **inner loop** (current control, 10 kHz) that makes the coils actually deliver that current despite the coil's own electrical dynamics and disturbances. This nested/cascaded control structure is completely standard in motor control: the fast inner loop keeps the electrical side well-behaved and linear-ish, so the slower outer loop can reason about mechanical dynamics without also fighting electrical transients.

## MATLAB/Simulink concepts you'll need

You know general programming; here's the vocabulary this project uses:

- **`.m` file**: a plain-text MATLAB script or function. Readable in any text editor, and this is where essentially all of the actual mathematics and logic in this project lives.
- **`.slx` file**: a *Simulink model* — a block diagram, saved as a binary (technically a zip-like container) file, not readable as text. Simulink is MATLAB's tool for building systems as connected blocks (signal sources, math blocks, custom code blocks, "scopes" that record data) rather than as a single script. This project has two: `models/SensoSpoon_Analytic.slx` (open-loop plant only) and `models/SensoSpoon_Control.slx` (closed loop, with the controller wired in).
- **You cannot read a `.slx` file's contents directly as text.** Because the diagrams are built *programmatically* by MATLAB scripts (`src/simulink/build_rcflex_analytic.m` and `src/control/build_rcflex_control.m`), you can understand their structure completely by reading those builder scripts — they call functions like `add_block` and `add_line` that literally construct the diagram, block by block, wire by wire. See `02_SIMULINK_MODELS.md`.
- **S-function**: a way to write a Simulink block's behavior in plain MATLAB code instead of dragging together pre-built blocks. A "Level-2 MATLAB S-Function" is a `.m` file with a specific structure (an `NumInputPorts`/`NumOutputPorts`/`Outputs`/`Derivatives`/`Update` set of callbacks) that Simulink calls at each simulation step. All of the "smart" blocks in this project (the physics plant, the sensors, the two controllers) are S-functions — meaning the actual algorithm is ordinary, readable MATLAB code, just wrapped so Simulink can call it as part of a block diagram.
- **Plant**: control-engineering jargon for "the physical system being controlled." Here, the plant is the electrical + mechanical + thermal model of the spoon mechanism (`rcflex_physics.m`).
- **Open-loop vs. closed-loop, specifically in this project**: "Open-loop" (`SensoSpoon_Analytic.slx`, `run_rcflex_analytic.m`) means you feed in a voltage command directly and watch what the mechanism does — there's no algorithm deciding the voltage, just whatever waveform you supply. "Closed-loop" (`SensoSpoon_Control.slx`, `run_rcflex_control.m`) means the voltage is decided at each instant by the sensor-feedback control system, forming the loop described above.
- **`mfilename('fullpath')`**: a MATLAB call that returns the path of the currently executing file — used here (`src/project_path.m`) so that file paths work regardless of MATLAB's "current folder," a common gotcha for MATLAB beginners.
- **Struct-based parameters**: instead of passing dozens of separate arguments, this project bundles related settings into a single MATLAB `struct` (e.g. `H` for hardware parameters from `rcflex_parameters.m`, `C` for controller parameters from `rcflex_control_parameters.m`). You'll see `H.something` and `C.something` constantly — think of it as a plain dictionary/record of named fields.
- **`timeseries`**: a MATLAB object pairing a matrix of data with a vector of time stamps, used to feed pre-computed signals (like a voltage command or a base-motion trajectory) into a Simulink "From Workspace" block.
